# 一、智能路由的真实目标（先校准）

> **不是“选成功率最高的渠道”**
> 而是在 **成功率、稳定性、成本、风控、容量** 之间做实时权衡

### 路由要解决的核心问题

| 维度  | 含义        |
| --- | --------- |
| 成功率 | 是否能付成功    |
| 稳定性 | 是否抖动      |
| 成本  | 通道手续费     |
| 容量  | 是否被打满     |
| 风控  | 商户 / 金额限制 |

# 五、② 渠道健康度评分模型（核心）

这是智能路由的灵魂。

---

## 1️⃣ 指标来源（Redis）

```text
stat:channel:5m:WECHAT_01
{
  total: 12000,
  success: 11500,
  avg_cost_ms: 420,
  fail_rate_trend: ↑
}
```

时间窗口建议：

* **1 分钟（实时）**
* **5 分钟（主判断）**
* **30 分钟（稳定性）**

---

## 2️⃣ 健康度评分公式（可直接用）

```text
score =
  W1 * success_rate
+ W2 * stability_score
+ W3 * latency_score
+ W4 * capacity_score
- W5 * cost_score
```

### 默认权重（可调）

| 指标  | 权重   |
| --- | ---- |
| 成功率 | 0.45 |
| 稳定性 | 0.20 |
| 延迟  | 0.15 |
| 容量  | 0.10 |
| 成本  | 0.10 |

---

## 3️⃣ 各指标如何计算（重点）

### ✅ 成功率（success_rate）

```text
success / total
```

* 低于阈值（如 90%）直接降权

---

### ✅ 稳定性（stability_score）

防止“刚刚很好，马上崩”的渠道

```text
stability = 1 - |success_rate_1m - success_rate_5m|
```

---

### ✅ 延迟评分（latency_score）

```text
latency_score = max(0, 1 - avg_cost_ms / 3000)
```

---

### ✅ 容量评分（capacity_score）

```text
capacity = 1 - current_qps / max_qps
```

（需要你给渠道配置一个理论上限）

---

### ❌ 成本评分（cost_score）

```text
cost_score = channel_fee_rate
```

---

## 4️⃣ 健康度分值示例

| 渠道        | score |
| --------- | ----- |
| WECHAT_01 | 0.82  |
| WECHAT_02 | 0.87  |
| ALIPAY_01 | 0.76  |

# 六、③ 权重选择（防止流量“全压死”）

❌ 错误做法：

> 永远选分最高的那个

这样会：

* 瞬间打爆单一通道
* 成功率反而下降

---

## 正确做法：**加权随机**

### 示例

| 渠道        | score | 权重 |
| --------- | ----- | -- |
| WECHAT_02 | 0.87  | 87 |
| WECHAT_01 | 0.82  | 82 |
| ALIPAY_01 | 0.76  | 76 |

按权重随机选。

---

## 伪代码

```java
Channel select(List<Channel> channels) {
    int sum = channels.stream().mapToInt(c -> c.weight).sum();
    int r = random(0, sum);
    for (Channel c : channels) {
        r -= c.weight;
        if (r <= 0) return c;
    }
}
```

# 七、④ 降级 & 兜底机制（救命用）

### 1️⃣ 快速熔断

```text
1 分钟内失败率 > 30%
→ 直接禁用 60 秒
```

### 2️⃣ 通道失败重试

```text
同一平台订单：
最多尝试 2 个不同渠道
```

### 3️⃣ 保底通道

```text
至少 1 个「稳定但贵」的通道
```

* 不查 MySQL
