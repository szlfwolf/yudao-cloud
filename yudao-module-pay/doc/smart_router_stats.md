# 一、闭环总览（一图理解）

```
        ┌────────────────────┐
        │  下单请求           │
        └─────────┬──────────┘
                  │
                  ▼
        ┌────────────────────┐
        │  智能路由引擎       │
        │  (规则 + 打分)     │
        └─────────┬──────────┘
                  │ 选择 channel
                  ▼
        ┌────────────────────┐
        │  上游支付渠道       │
        └─────────┬──────────┘
                  │ 支付结果
                  ▼
        ┌────────────────────┐
        │  订单状态机         │
        └─────────┬──────────┘
                  │ 终态事件
                  ▼
        ┌────────────────────┐
        │  统计事件总线 (MQ)  │
        └─────────┬──────────┘
                  │
      ┌───────────┴───────────┐
      │                       │
      ▼                       ▼
┌──────────────┐      ┌────────────────┐
│ 实时统计     │      │ 汇总统计       │
│ (Redis)      │      │ (MySQL / OLAP) │
└──────┬───────┘      └────────────────┘
       │
       ▼
┌────────────────────┐
│ 路由数据快照服务   │
│ (Cache / Redis)   │
└────────────────────┘
       │
       └──────► 回流到路由引擎
```

👉 **统计不是“旁路”，而是路由的输入**

# 二、闭环的 4 类核心数据（必须分清）

## 1️⃣ 路由决策输入数据（只读）

| 数据     | 来源         | 更新频率  |
| ------ | ---------- | ----- |
| 渠道成功率  | Redis 统计   | 1～5 秒 |
| 渠道延迟   | Redis 统计   | 1～5 秒 |
| 渠道失败趋势 | Redis 统计   | 30 秒  |
| 容量使用率  | 内存 / Redis | 实时    |

⚠️ **禁止路由引擎直接查交易表**

---

## 2️⃣ 路由决策输出数据（要记录）

每一次路由决策都要**留痕**，否则后面解释不了问题。

```json
{
  "platform_order_no": "P202601080001",
  "candidate_channels": ["WECHAT_01","WECHAT_02"],
  "selected_channel": "WECHAT_02",
  "score_snapshot": {
    "WECHAT_01": 0.82,
    "WECHAT_02": 0.87
  },
  "decision_time": "2026-01-08T10:01:12"
}
```

### 存储方式

* **只写 MQ / ES / 冷表**
* 不影响主链路

---

## 3️⃣ 交易结果统计数据（反馈）

来自订单终态事件：

```json
{
  "event_type": "PAY_SUCCESS",
  "channel_code": "WECHAT_02",
  "amount": 100.50,
  "latency_ms": 430
}
```

---

## 4️⃣ 路由调控数据（反作用）

| 类型   | 用途    |
| ---- | ----- |
| 熔断状态 | 强制禁用  |
| 权重修正 | 人工干预  |
| 灰度比例 | 新渠道放量 |

# 三、闭环时序（一步一步）

## Step 1：下单触发路由

```
下游请求
 → 路由引擎拉取「渠道统计快照」
 → 计算 score
 → 选择 channel
```

📌 **快照原则**

* 每个请求只用一份快照
* 不允许路由中途变更

---

## Step 2：记录路由决策（旁路）

```
路由结果
 → 异步写 MQ / ES
```

用途：

* 事故回溯
* AB 测试
* 算法优化

---

## Step 3：交易完成 → 发统计事件

```
订单状态 SUCCESS / FAIL
 → 发 PAY_RESULT_EVENT
```

---

## Step 4：统计服务消费 & 聚合

```
事件
 → Redis 实时统计
 → MySQL / OLAP 汇总
```

---

## Step 5：生成“路由可用快照”

### 快照内容（示例）

```json
{
  "channel_code": "WECHAT_02",
  "success_rate_1m": 0.98,
  "success_rate_5m": 0.96,
  "avg_latency": 420,
  "health_score": 0.87,
  "circuit_break": false
}
```

* 由统计服务定时计算
* 写入 Redis

---

## Step 6：路由引擎热更新

```
Redis → 本地缓存（Caffeine）
刷新周期：1～5 秒
```

# 四、防“自激振荡”的关键设计（非常重要）

> 很多智能路由系统不是被“算错”，而是被**自己抖死的**

---

## 1️⃣ 冷启动保护

```text
新渠道：
前 1000 单不参与评分
固定 5% 流量
```

---

## 2️⃣ 评分变化限速（Rate Limit）

```text
health_score 单次变动 ≤ ±5%
```

防止一波失败直接打死通道。

---

## 3️⃣ 滑动窗口 + EMA

```text
score = 0.7 * score_5m + 0.3 * score_1m
```

---

## 4️⃣ 熔断恢复不是立即的

```text
熔断 60s
→ 半开 10% 流量
→ 观察
```

# 五、运维 / 人工干预闭环（必备）

## 人工可以干预的 4 件事

| 操作      | 作用   |
| ------- | ---- |
| 强制下线渠道  | 紧急事故 |
| 手动调权重   | 商务谈判 |
| 设置商户白名单 | 特殊商户 |
| 调整成本权重  | 利润策略 |

### 干预原则

> **人工优先级 > 算法**
